## 修复：使用统计刷新后 Grok/OMP 显示 0（三处解析 bug）

- 现象：点「重新统计」后 Grok/OMP 合计 0；Kimi/OpenCode 也悄悄走了近似兜底。
- 根因 1（Grok）：`extract_skill_names` 取「最后一个 / 之后」的段，对 `…/orchestration/SKILL.md` 取到空串——技能名在倒数第二个斜杠与最后一个之间。修复：先 `trim_end_matches('/')` 再 `rfind('/')`。
- 根因 2（OMP）：read 工具调用不是 `"name":"read"` 而是 custom 事件 `"toolName":"read"`（`"args":{"path":…}`）；另有真实信号 `customType:"skill-prompt"`（技能注入，3 次）。行内自带 timestamp，趋势可精确到天。
- 根因 3（通用，最隐蔽）：`extract_value` 的 key 以引号结尾时（如 `"path":"`），find 后 rest 不以引号开头 → 误走数字分支返回 None。所有引号结尾 key 全部中招，包括 OpenCode 的 `"input":{"name":"`（叠加 `substr(data,1,600)` 截断，改 instr 定位）。教训：**key 统一以冒号结尾，函数内消费可选引号**。
- 副作用修复：scan_kimi/scan_opencode 对未安装技能不再丢弃（fallback 记原名）；claude exact 22 与独立核对一致。
- 缓存策略：`get()` 现在要求 supported && total>0 && trend 非空才用缓存，历史错误 0 值打开页面即自愈。
- 验证方式：在 usage.rs 写 `#[cfg(test)]` 用真实 home 目录跑 scanner（cargo test -- --nocapture），比 python 模拟可靠；保留 `extract_skill_names_regression` 断言测试。
- 数据：Grok 20（orchestration 6/orca-cli 6/spring-boot 3/mysql-query 2/其余各 1）、OMP 5、OpenCode 14、Kimi 1。
- 注意：Edit 工具再次假成功（key 修复未落盘），python 读改写 + grep 验证才可靠。

## 禁用机制改造：从「skills 下加 . 前缀」改为「skills 同级 disabled-skills/」

- 老曹提出的质疑成立：`.foo` 是否会被 agent 加载取决于各 agent 实现，**不是保证**。查证结果：
  - Codex（codex-rs/core/src/skills/loader.rs）：BFS 遍历，**明确跳过 `.` 开头**目录/文件 → 安全。
  - OpenCode：用 glob 模式 `skills/**/SKILL.md`，是否跳隐藏目录取决于 glob 库的 dot 选项，文档未承诺 → 不确定。
  - Claude Code：闭源，未公开约定 → 不确定。
  - 另有一类现实风险：社区脚本/第三方工具常用 `find ~/.xx/skills -name SKILL.md`，不排除隐藏目录。
- 结论：**唯一确定性的隔离是把目录移出 skills 树**。
- 实现：`adapters::disabled_dir(adapter)` = skills 目录的父目录 + `disabled-skills`（如 ~/.claude/skills → ~/.claude/disabled-skills）。
  - fsops::disable_skill：rename 到 disabled-skills/<folder>（自动 create_dir_all）。
  - fsops::enable_skill：优先从 disabled-skills 取回；**兼容旧版** skills 下 `.folder`（当前环境无旧数据）。
  - scanner::scan_local：额外扫描 disabled-skills/，条目 disabled=true；skills 下 `.` 前缀仍按 disabled 识别（旧数据兼容）。
  - 新增 `validate_folder()` 做单层目录名校验；新增测试 `disabled_dir_sits_outside_skills_dir` 钉住「禁用目录必须在 skills 之外」。
- 前端：确认弹窗文案改为显示目标路径（helpers `disabledDest()`），MatrixPage 悬浮说明同步更新。
